# DuckDB 2.0 for new and existing deployments

Liwan already bundles DuckDB 2.0: `duckdb` is on the `1.20000` line
(`crates/liwan/Cargo.toml:96`), which resolves to `1.20000.2` and bundles
DuckDB 2.0.0, and `liwan upgrade-duckdb` exists (`crates/liwan/src/cli.rs:50`,
`upgrade_db` at `cli.rs:265`) with tests. But an instance that updates from
1.8.x keeps its event database in the old storage format, and nothing tells its
operator that the converter exists: there is no startup signal, no README
section, and no release note. The converter is also only tested against a toy
table, not a database with the real schema, and it never checks the copy it
produces before replacing the original.

      original and any `.old` file untouched. Extend
      `upgrades_database_and_keeps_backup` to assert that the table list survives the
      copy, including the `migrations` table when the source has one. Keep the
      existing refusals: symlink, non-file, WAL present, `.old` or `.upgrade` already

- [x] Document the command in `README.md` under a new `## Upgrading` section
      between `## Features` and `## License`, using this text (adjust only for
      80-column wrapping):

  ````markdown
  ## Upgrading

  Liwan stores events in DuckDB 2.0. Databases created by earlier versions keep
  working without changes; they are only rewritten into the new storage format
  when you ask for it.

  To rewrite one, stop Liwan and run:

  ```sh
  liwan --config /path/to/liwan.config.toml upgrade-duckdb
  ```

  Pass a database path instead to upgrade a file elsewhere:

  ```sh
  liwan upgrade-duckdb /path/to/liwan-events.duckdb
  ```

  The command writes the converted database next to the original, checks it, and
  keeps the original beside it with an `.old` suffix (`liwan-events.duckdb.old`
  for the default database). It needs free disk space for a second copy of the
  database, and it fails if the database is in use or has an uncommitted
  write-ahead log. The conversion is one-way: a converted database cannot be
  opened by Liwan releases that bundle DuckDB 1.x.
  ````

## Implementation context

**Already on `main`, not part of this plan.** Commit `c26bdbc` (2026-10-26)
moved `duckdb` from `=1.10506` to `1.20000`, adapted the report queries, and added
`UpgradeDuckDb` / `upgrade_db` with `cli::tests` coverage. The engine and the
command therefore exist; this plan adds the rollout around them. Do not re-bump
the crate, rename the subcommand, or rewrite `upgrade_db` from scratch.

**Decisions (2026-11-15).**

- Conversion stays an explicit command, never automatic on startup. The copy is
  roughly the size of the original, needs a second copy on disk, and is one-way;
  an operator's only database must not be rewritten unattended.
- The signal is a single startup log warning, not a dashboard banner. A v1 file
  works fine with a v2 engine, and the action is operator-only; a banner would
  add a dismissible UI state and a settings key for no functional gain.
- Keep the name `upgrade-duckdb`. It is already on `main` and the README and
  release notes will refer to it; renaming it before the next release would only
  make the notes and the binary disagree with each other.
- A converted file cannot be opened by a Liwan release that bundles DuckDB 1.x.
  That is documented in the README; it is not a changelog Breaking Change, because
  updating Liwan does not convert anything by itself.
- No new config key and no `data/config.example.toml` change: the storage format is
  a property of the file, not an operator setting. No API or wire-format change,
  no new events migration number, and no change to `packages/api` or `crates/api`.

**Landmarks.**

- `crates/liwan/src/app/db.rs:11` `init_duckdb`, `:51` pool creation, `:54`
  pragmas, `:59-72` migration runner; `init_duckdb_mem` is the in-memory path and
  needs no check.
- `crates/liwan/src/app/mod.rs:55` `Liwan::try_new` calls `init_duckdb` with
  `data_dir/liwan-events.duckdb`.
- `crates/liwan/src/cli.rs:50` subcommand, `:212` dispatch, `:265` `upgrade_db`,
  `:305-400` existing tests.
- `README.md` has no upgrade section today; `CHANGELOG.md` starts at `v1.8.1`
  (2026-10-23), before `c26bdbc`, so the next section must be `Unreleased`.
- `tempfile` is already a dev-dependency; add no dependency.

**Slices.**

- Slice 1 (startup warning): `app/db.rs` now has `warn_on_outdated_storage_version`
  called from `init_duckdb` after the migration runner, and `storage_major`, which
  reads the digits after the leading `v` (`v2.1.0+` and `v2.0.0+` both give 2; a
  bare `v2` also parses, everything without `v<digits>` is `None`). A `None`
  version or a failed query is `tracing::debug!` only, so startup cannot break;
  the warning fires for majors below 2 and mentions `liwan upgrade-duckdb`, a
  stopped Liwan, and the `.old` copy. Tests: `app::db::tests::storage_major_reads_the_leading_version`
  and `storage_major_rejects_malformed_versions`.
- The query reads `tags['storage_version']` from the attached file itself (not
  `system`/`temp`), so it works for both a fresh file and one opened from
  `data_dir/liwan-events.duckdb`; no extra attach step is needed.
- Slice 2 (fresh-install guard): `app::db::tests::fresh_database_is_written_in_the_v2_storage_format`
  builds a real file in a `tempfile` dir through `init_duckdb` and asserts the
  tag starts with `v2.`. It fails if a future `duckdb` bump resolves the engine
  back to the 1.x line, and it runs in the default `cargo test --lib` pass with
  no fixture on disk. `tempfile` is already a dev-dependency; nothing new was
  added, and no `storage_compatibility_version` was configured for the app.
- Slice 3 (verified copy): inside the attached block in `cli.rs::upgrade_db`,
  after the `COPY` and `CHECKPOINT`, the copy's `tags['storage_version']` must
  start with `v2.`, and sorted `duckdb_tables()` names for `liwan_source` and
  `liwan_upgraded` must match. Both failures `bail!` with the `.upgrade` path and
  happen before any rename, so the original and an existing `.old` stay as they
  were. A failed run leaves the `.upgrade` file behind (as the existing COPY
  failure did), which names it in the message and makes the next attempt refuse
  until the operator deletes it. The fixture in `upgrades_database_and_keeps_backup`
  now creates a `migrations` table next to `events` and asserts both files list
  the same tables; a mismatch cannot be produced from a healthy DuckDB, so that
  branch has no test.
- `duckdb_tables()` is enough here: the events schema is one `events` table plus
  refinery's `migrations` table, with no views. `COPY FROM DATABASE` carries both.
- Slice 4 (docs): `README.md` has a `## Upgrading` section between `## Features`
  and `## License` with the roadmap text verbatim, wrapped under 80 columns. It
  documents stopping Liwan, both command forms, the `.old` backup, the free-disk
  and WAL requirements, and the one-way conversion; keep it in sync if the
  command's flags or side effects change.
- Slice 5 (changelog): `CHANGELOG.md` now starts with `## [Unreleased]`. One
  `### Features` bullet leads with `upgrade-duckdb` in backticks and covers what
  updating does not do, stopping Liwan, the `.old` copy and the one-way format;
  one `### Other` bullet says Liwan now bundles DuckDB 2.0 and existing databases
  keep working. No command line, file path or crate version. The startup warning
  and the copy verification are internal signals and are covered by the Features
  bullet rather than listed separately.
- Changelog voice check: "event database" and "storage format" are the terms the
  README uses; DuckDB 2.0 is the engine version the roadmap asked to name, not a
  crate version.

**End-to-end check (2026-11-15, local).** A throwaway helper created a
`storage_compatibility_version = v1.5.0` file in a temp `data_dir`, then

- `liwan --config <file> users` logged the new warning once
  (`storage_version=v1.5.0+`) and left the file at v1.5.0 with the real
  `events` and `migrations` tables;
- `liwan --config <file> upgrade-duckdb` reported the upgrade, wrote a `.old`
  beside it and both files were 780 KiB; the converted file read `v2.0.0+` and
  the backup `v1.5.0+`, each with the same three tables;
- the next `users` run logged no storage warning.

The seeded 10,000,000-event pass in "How to prove it" was not run: the copy path
does not depend on row count, and the unit tests plus this run cover the format
and the table list. Re-run it before a release if the copy code changes.

**How to prove it.**

- `mise exec -- cargo test -p liwan --lib` covers the parser, the fresh-database
  test, and the hardening tests.
- `mise run rust:test` and `mise run rust:lint` are what CI runs; the HTTP tests
  need a free local socket, which CI provides.
- End to end with real data: `mise run web:build`, then `mise exec -- cargo dev
seed` against a checkout-local `data_dir`, stop the process, run
  `mise exec -- cargo run -- upgrade-duckdb`, restart, and open the dashboard.
  A database seeded by current `main` is already `v2.0.0+`, so this proves the
  copy and the restart, not the v1 conversion; the v1 path is covered by the
  `cli::tests` fixture created with `storage_compatibility_version = v1.5.0`.
  Record the version and file sizes before and after in the commit body. Do not
  claim a speed-up unless the seeded benchmark shows one.

**Out of scope.** A dashboard banner or settings key for the storage version, an
automatic conversion on startup, a rename or an alias for the command, changes to
the report SQL (done in `c26bdbc`), and the liwan.dev documentation site, which is
not in this repository.
