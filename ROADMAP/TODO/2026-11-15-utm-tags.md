# UTM tags screen for projects

Liwan extracts and reports UTM parameters, but a team has nowhere to keep the
tagged links it uses. There is no way to save a campaign link, see how much
traffic it brought in, or open the report filtered to that exact link. This plan
adds a UTM tags screen to each project: save a name, a destination URL, and the
five UTM values, copy the finished link, see pageviews and unique visitors for
the selected range, and open the report filtered to the tag.

## Implementation context

**Decisions (2026-11-15).**

- The screen lives on the project dashboard at `/p/<project>/utm-tags`, not in
  project settings. The user asked for a project screen, and the project
  settings detail page is admin-only, which would hide the links from the
  viewers who can already see the project.
- This plan owns the shared project chrome: `ProjectNav` and
  `getDashboardProjectId()`, plus moving the report page onto the helper. The
  funnels plan adds only the `Funnels` link to the same row when its page
  ships. The user chose this split so neither plan writes a second navigation
  row or a second path parser. If the funnels page ships before the UTM screen,
  its worker creates the same row with Overview and Funnels from this spec and
  leaves the UTM link to this plan; this plan still owns later changes to the
  shell.
- Reading the list and the summary follows the project's existing visibility:
  anyone who can view the project, including anonymous visitors of a public or
  unlisted project, can read them. Creating, editing, and deleting require the
  admin role because the dashboard has no project-write permission, and letting
  an anonymous viewer change a public project's links would be unsafe. This is
  the one place where a public project exposes saved links; they are outbound
  marketing links, not analytics records. If that changes, require `Admin` on
  the read routes too.
- A tag stores a friendly name, a destination URL, and the five UTM values.
  Each value is optional, but at least one is required: a tag with no UTM value
  cannot match traffic or filter a report and would only be a bookmark.
- The inline summary is pageviews and unique visitors per tag for the selected
  range. Pageviews match the report's default metric; bounce rate and average
  time would pull session-bound semantics into a link manager and are out of
  scope. There is no grand total because tags can overlap and a sum would
  double-count.
- The screen shares the dashboard's persisted date range, so changing it here
  also changes what the report opens with. One range control and one mental
  model beat a second range stored only on this screen.
- `View traffic` applies every UTM value set on the tag as an `equal` filter.
  A partial tag therefore opens a broader report, which is the honest meaning
  of a tag with only a source. The link is a generic `filters` JSON parameter
  because that matches the report's `DimensionFilter` model and does not
  reserve the `utm_*` query names, which a tagged dashboard link could
  accidentally supply.
- The report rewrites the `filters` parameter as filters change, with
  `replaceState` rather than a navigation. Without that, removing a seeded
  filter would leave a stale URL that comes back on refresh. Putting the date
  range or metric in the URL is a separate concern and stays out of this plan.
- The client builds the tagged URL; the server validates the base URL and
  stores the fields. The dialog preview and every copy button then share one
  implementation, and the API remains plain CRUD. Re-serializing URLs on the
  Rust side would be a second normalization rule that could disagree with the
  browser.
- The base URL is stored as the user typed it after trimming. A pasted URL
  with existing UTM parameters does not populate the fields; the five fields
  are authoritative, and the generated link removes any managed `utm_*`
  parameter before applying them. This avoids a hidden stale value.
- The summary and the report link use the dashboard's existing `equal`
  semantics (`ilike`), so the number in the row and the number after `View
  traffic` agree. That also means `%` and `_` in a tag value act as LIKE
  patterns, which is pre-existing filter behavior; changing equality matching
  is a separate change, not part of this plan.
- The summary runs as one grouped query over the range and a values table of
  the project's tags, rather than one query per tag. It returns a row for every
  tag, with zeros for no traffic, so the table never has to fill holes.
- The summary refreshes every 60 seconds only while the range ends today,
  matching the custom-events card. Historical ranges do not change.
- The list is ordered by name, case-insensitive, then id. A manager scans by
  name, and editing a tag should not make the row jump. Names are not unique:
  two tags can use the same campaign parameters on different landing pages,
  and the URL tells them apart.
- Deleting a tag removes the saved link only. Sessions already recorded are not
  touched, and editing a tag's UTM values changes only what future summaries
  match; the page says so.
- Limits are fixed rather than configurable: a name is 1 to 100 characters, a
  URL at most 2048 bytes, and each UTM value at most 200 bytes. These are
  project records, not deployment behavior, so there is no config key and no
  `data/config.example.toml` change.
- V9 belongs to the funnels plan
  ([2026-11-15-project-funnels.md](2026-11-15-project-funnels.md)), which was
  committed first and explicitly claims it. This plan takes V10 even if it
  ships first; a gap while V9 is unshipped is safe because refinery applies
  available versions in order, and the funnels migration is independent. Never
  edit a migration that has shipped.
- The dashboard OpenAPI definition changes, so `packages/web/src/api/dashboard.ts`
  is regenerated and committed. `packages/api` and `crates/api` only cover
  event ingestion and do not change.

  `mise exec -- cargo run`, and open

- Check the screen with the `browser` tools at desktop and 360px widths, in

  the page, the dialog is keyboard usable, and every icon button has an

- Check the page and the `ProjectNav` links under a `base_url` with a sub-path.

  configured base path, not only at the root.

**Out of scope.**

- Renaming, merging, or aliasing UTM values already stored in events.
- Global UTM tags shared across projects, or a tag manager under Settings.
- Auto-extracting UTM parameters from a pasted URL into the form; the five
  fields stay authoritative.
- Search, filtering, sorting, bulk import, bulk export, or manual ordering on
  the tag list.
- Bounce rate and average time on site in the summary.
- Putting the date range or metric in the report URL; only `filters` is added.
- Changes to `packages/api` or `crates/api`, which are event-ingestion clients.
- A config key or `data/config.example.toml` entry for tag limits.
- The liwan.dev documentation site, which is not in this repository.

**Build notes.**

- App migration numbering: `main` already ships `V11__indexes.sql` (the
  backend-performance plan), so `V10__utm_tags.sql` fills a gap below the latest
  applied version. Refinery applies unapplied versions in ascending order, so a
  V10 next to an already-applied V11 is applied on the next start, and a later
  V9 from the funnels plan is picked up whenever it lands. Verified by the
  in-memory app tests, which run every embedded migration on each start.
- Store: `crates/liwan/src/app/core/utm_tags.rs` holds `LiwanUtmTags` and the
  shared `validate_utm_tag` that returns a normalized `UtmTagInput`; create and
  update both call it before any write, so an invalid update leaves the stored
  row untouched. `UtmTagInput` and `LiwanUtmTags` are re-exported from
  `crates/liwan/src/app/mod.rs` for the HTTP layer.
- Validation detail: the destination URL is also rejected when it contains
  control characters, which `url::Url::parse` alone does not catch because the
  URL standard strips ASCII tab and newline before parsing. A tag whose values
  are all empty after trimming is rejected instead of stored as a bare bookmark.
  Note that `url::Url::parse("https:///path")` succeeds with host `path`; the
  "absolute http(s) with a non-empty host" rule is implemented against the
  parsed URL, not the raw string.
- The model `UtmTag` intentionally has no `created_at`/`updated_at` fields: the
  table keeps both for ordering and auditing, but no API response exposes them.
- The tag stores the six identity fields and the timestamp columns only; no
  cached counts, because the summary is always computed for the selected range.
- HTTP shape, as committed: `GET` and `POST /api/dashboard/project/{project_id}
  /utm-tags`, `POST .../utm-tags/summary`, `PUT` and `DELETE
  .../utm-tags/{tag_id}`, all merged into the dashboard router from
  `crates/liwan/src/web/routes/utm_tags.rs`. Requests send `displayName`, `url`,
  and the five `utm*` fields, with the five optional ones defaulting to null;
  the list response is `{ utmTags: [...] }`, the summary response is
  `{ summaries: [{ id, totalViews, uniqueVisitors }] }`. The summary request is
  `{ range: { start, end } }`, one range, validated with
  `reports::validate_request` against an empty filter list and the configured
  report limits.
- `run_report` and `report_project` in
  `crates/liwan/src/web/routes/dashboard.rs` are `pub(super)`, so the UTM tag
  module reuses the existing permit, connection timeout, and interrupt handling
  instead of copying them. The mutations look the project up for a 404 because
  `Admin` alone does not prove the project exists; reads go through
  `report_project`, so `can_view_project` and the 404 behave exactly like the
  report handlers.
- Commit order inside the feature differs from the checklist: the summary query
  landed in its own commit before the routes, because the summary handler cannot
  compile or pass its test without it. Item 3 still owns the query's benchmark
  and its tick.
- The `filters` parameter holds plain JSON in the URL; `URLSearchParams` does
  the percent-encoding on both sides, so `serializeReportFilters` returns the
  JSON text (or `null` for an empty list) and `parseReportFilters` takes a search
  string. The parser also enforces the server's own rules on the entries it
  keeps: `is_true`/`is_false` belong to `mobile` only, a property filter needs a
  key, and a key on any other dimension is dropped instead of making the report
  return 400.
- `packages/web/src/components/dashboard/project/index.tsx` calls
  `history.replaceState` in an effect keyed on the filters, so the URL is
  rewritten, not navigated to, and an invalid `filters` value is cleaned up on
  load.
